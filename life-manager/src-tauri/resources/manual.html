Life Manager マニュアル

タスク管理と、git によるバージョン管理を、画面で見ながら行うためのアプリです。

このマニュアルは、左のサイドバーから「作業」「ブランチ」「全体図」を使える版（0.9 以降）に合わせています。

はじめに

Life Manager は、GitHub のリポジトリを使って、次の 2 つをまとめて行うアプリです。

  • タスク管理: やること（Issue）を作り、状態や期限、目標（マイルストーン）で整理します。
  • バージョン管理: ファイルの変更を git で記録し、GitHub に送ります。どの操作でも、実際に実行される git のコマンドが画面に表示されるので、使いながら git を覚えられます。

データはすべて GitHub のリポジトリに保存されます（Issue・マイルストーン・ラベル・設定ファイル）。アプリを消しても、データは GitHub に残ります。

学ぶためのしかけ

「作業」タブでは、今どの段階にいるのか（Issue を選ぶ → ブランチ → 変更 → コミット → プッシュ → 完了）と、次に何をすればよいかを案内します。ステージやコミットなどの意味の解説も表示されます（設定 → 表示 で消すこともできます）。

インストール

  1. 配布されたインストーラー（Life Manager_x.x.x_x64-setup.exe）を実行します。
  2. 画面の案内に沿ってインストールします。
  3. 最後に、Git が入っているかを調べます。入っていなければ「今すぐ Git をインストールしますか？」と聞かれます。はい を押すと、Git を自動でインストールします（数分かかります）。
  4. 終わったら、スタートメニューかデスクトップから Life Manager を起動します。
「このアプリがデバイスに変更を加えることを許可しますか？」と出たら

Git のインストールには、PC の管理者の確認が必要です。はい を押してください。学校や会社の PC で管理者の確認ができないときは、PC の管理者に Git のインストールを頼んでください。

インストールのときに いいえ を選んだ場合や、うまく入らなかった場合も、アプリを起動したときにもう一度案内が出ます（「使う準備」）。

新しいバージョンが出ると、アプリの上に「新しいバージョン … が利用可能です」と表示されます。今すぐ更新 で更新できます。

初期セットアップ

はじめて起動すると、セットアップの画面が出ます。3 つのステップで終わります。トークンを自分で作る必要はありません。

ステップ 1: GitHub にログイン

  1. GitHub でログイン を押すと、ブラウザで GitHub が開き、アプリに 8 文字のコード（例 WDJB-MJHT）が出ます。
  2. ブラウザでコードを入れて Continue → Authorize を押します（GitHub にログインしていなければ、先にログインします）。
  3. アプリに戻ると「○○ としてログインしています」と出て、次に進みます。
ログインで許可すること

Life Manager が、あなたの代わりに、あなたが入っているリポジトリの Issue とファイル（設定・日誌）を読み書きできるようになります。パスワードはアプリに渡りません。やめたいときは、GitHub の Settings → Applications → Authorized OAuth Apps から取り消せます。

ステップ 2: 使うリポジトリを選ぶ

自分が使えるリポジトリ（自分のもの・招待されたもの・入っている組織のもの）が、新しく使った順に出ます。選ぶと、使えるかをその場で確かめます。一覧になければ、URL（https://github.com/持ち主/名前）を貼っても選べます。

チームのリポジトリが出てこない・「組織の許可がまだです」と出る

組織（Organization）のリポジトリは、組織の管理者が一度だけ Life Manager を許可すると使えるようになります。組織に許可をお願いする を押すと GitHub が開くので、組織の横の Request（管理者なら Grant）を押します（「チームで使う」）。招待をまだ受けていない（メールの「Accept invitation」を押していない）ときも出てきません。

ステップ 3: できあがり

はじめる を押すと、タスクの画面になります。PC では続けて、git を使う準備（Git のインストール・コミットに使う名前）の案内が出ます。

ヒント

接続したら、設定 → ラベル の ラベル一括作成 を一度押しておくと、Life Manager で使うラベル（種別・分野・状態・優先）がリポジトリに作られます。

トークンで入る（学校で指定されたときなど）

ログインの画面の下の トークンで入る から、自分で作ったトークン（Fine-grained token）でも使えます。

  1. GitHub で作る を押すと、名前・期限（90 日）・権限が入った状態で、GitHub のトークンの作成ページが開きます。
  2. Repository access で Only select repositories を選び、使うリポジトリを選びます（ここだけは自分で選びます）。組織のリポジトリなら、Resource owner を組織にします。
  3. Generate token を押し、出てきたトークン（github_pat_ で始まる文字列）をコピーして、アプリに貼ります。貼るとすぐ、だれのトークンか・期限・リポジトリが見えるかを確かめ、足りないときは直し方が出ます。

スマホでは、下のナビゲーションで「タスク」「ボード」「マイルストーン」「ルーチン」「日誌」「ガント」「設定」を切り替えます。

git のしくみ（まずここから）

git は、ファイルの変更を「いつ・だれが・何を変えたか」として記録する道具です。記録の単位をコミットと呼びます。Life Manager の「作業」タブは、次の流れをそのまま画面にしています。

ブランチは、作業を分けて進めるための「流れ」です。たとえば Issue ごとにブランチを作って作業し、終わったら元のブランチにマージ（合流）します。こうすると、途中の作業がほかの作業と混ざりません。

使う準備（Git・名前・作業フォルダ）

「作業」「ブランチ」「全体図」で git を使うための準備です（PC のみ）。

Git のインストール

アプリを起動したとき、Git が入っていなければ「Git をインストールしますか？」と表示されます。インストールする を押すと、Git を入れます。

# Windows で実行されるコマンド（Windows に入っている winget を使います） winget install --id Git.Git -e --source winget

winget が使えない PC では、Git for Windows の公式のインストーラーを GitHub から取ってきて実行します。Mac では、Git が入った「コマンドライン ツール」のインストール画面が出ます。

あとでインストールする場合は、設定 → 接続 の「作業フォルダ（この PC）」にある Git をインストールする… からも入れられます。起動のたびに案内が出てほしくないときは、案内の画面で「次からは起動時に表示しない」にチェックを入れます。

コミットに使う名前とメールアドレス

コミットには、だれが変更したかを残すため、名前とメールアドレスを付けます。決まっていないと、案内の画面で入力を求められます。はじめから、GitHub のアカウントの名前と、GitHub が用意する公開用のアドレス（…@users.noreply.github.com）が入っています。

git config --global user.name "名前" git config --global user.email 12345+ユーザー名@users.noreply.github.com
なぜ noreply のアドレス？

コミットに付けたメールアドレスは、GitHub で公開されます。GitHub が用意する noreply のアドレスを使うと、ふだんのメールアドレスを知られずに、コミットを自分のアカウントに結びつけられます。

今の設定は、設定 → 接続 → 作業フォルダ の 使う準備を確かめる で見られます（変更もできます）。

作業フォルダを決める

作業フォルダは、リポジトリのファイルを置く、この PC 上のフォルダです。設定 → 接続 の「作業フォルダ（この PC）」か、作業タブで決めます。

ボタン使うときすること
GitHub からクローン…まだ PC にリポジトリがないとき選んだフォルダの中に、リポジトリと同じ名前のフォルダを作ってコピーします（git clone）。
フォルダを選ぶ…すでにクローンしてあるときそのフォルダが、設定しているリポジトリのものかを確かめてから使います。中のフォルダを選んでも、リポジトリのいちばん上のフォルダになります。
設定を外す別のフォルダにしたいとき設定だけを外します。フォルダやファイルは消えません。
# クローンのときに実行されるコマンドの例 git clone https://github.com/オーナー名/リポジトリ名.git D:\work\リポジトリ名

作業フォルダは PC ごと・リポジトリごとに覚えます。設定 → 接続 のプロジェクト一覧では、フォルダが決まっているリポジトリに 📁 が付きます。

作業フォルダがない PC やスマホでも、「ブランチ」「全体図」は GitHub にある状態を表示でき、コミットの 変更内容を見る も使えます（見るだけで、操作はできません）。

ほかのリポジトリを追加する（URL を貼ってクローン）

設定 → 接続 → プロジェクト管理 の ＋ 追加 で、GitHub のリポジトリの URL を貼ります（https://github.com/持ち主/名前、git@github.com:持ち主/名前.git、持ち主/名前 のどれでも）。この PC にも持ってくる（クローン） にチェックを入れると、置き場所を選んでクローンし、そのフォルダを作業フォルダにします。チェックを外すと、プロジェクトに登録するだけです。

手元のフォルダを GitHub に上げる

まだ GitHub に無いフォルダ（課題や作品のフォルダ）は、＋ 追加 の画面の下の GitHub にまだ無い → 手元のフォルダを GitHub に上げる から、4 つの手順で上げられます。

  1. 記録を始める: 上げるフォルダを選びます。まだ Git の記録がなければ、記録を始め（git init）、.gitignore のひな形（Visual Studio / Unity / Unreal Engine）を置いて、今の中身を最初のコミットにします。
  2. GitHub に場所を作る: GitHub で作る でブラウザが開きます。README や .gitignore は付けずに「Create repository」を押し、戻って 作ったので次へ を押します（リポジトリができたかを確かめます）。
  3. つないで送る: GitHub の置き場所を origin という名前で登録し、送ります（git push -u）。
  4. できあがり: プロジェクトに登録し、このフォルダを作業フォルダにします。
# 実行されるコマンドの例 git init -b main git add . git commit -m "最初のコミット" git remote add origin https://github.com/持ち主/名前.git git push -u origin main

ほかのリポジトリの中にあるフォルダは上げられません。GitHub は 100MB を超えるファイルを受け付けないので、そういうファイルがあるときは、コミットする前に知らせます（記録しないなら .gitignore に書き、記録するなら Git LFS を使います）。

作業タブ

取り組む Issue を決めて、ファイルの変更をコミットし、GitHub に送るまでを進める画面です。

取り組み中の Issue

上の 取り組み中の Issue から、未完了の Issue を選びます（番号やタイトルで絞り込めます。進行中のものが先に並びます）。Issue なしで作業するときは Issue なしで作業する を選びます。

  • Issue を開く: Issue の詳細を開きます。
  • 進行中にする: Issue の状態を「進行中」にします。

選んだ Issue は、リポジトリごとにこの PC に覚えておきます。

作業の流れ

今どの段階にいるかが光り、下に次にすることと、そのためのボタンが表示されます。

  1. Issue を選ぶ何をするかを決める
  2. ブランチ作業する場所（既定のブランチにいるときは、Issue 用のブランチを作る案内が出ます）
  3. 変更ファイルを編集して、入れたい変更にチェック
  4. コミット要約を書いて記録する
  5. プッシュGitHub に送る
  6. 完了Issue を閉じる

変更とステージ（「変更」タブ）

編集したファイルが一覧に出ます。チェックを入れたファイル（ステージ済み）が、次のコミットに入ります。

操作意味コマンド
未ステージのファイルにチェック次のコミットに入れるgit add -- ファイル
ステージ済みのファイルのチェックを外す次のコミットから外す（変更は残る）git restore --staged -- ファイル
すべてステージすべての変更を入れるgit add -- .
すべて外すすべてを外すgit restore --staged -- .

ファイルの左の文字は、変更の種類です。

文字意味
A追加したファイル
M変更したファイル
D削除したファイル
R名前を変えたファイル
?まだ git が追跡していない新しいファイル（チェックを入れると追加になります）
U競合しているファイル（「競合したとき」）

ファイルを選ぶと、右に差分（変更の中身）が出ます。緑の行が追加、赤の行が削除です。+12 −3 は、追加した行と削除した行の数です。一覧の下には、直前に実行したコマンドが表示されます。

記録しないファイル（.gitignore）

ビルドの結果・ログ・エンジンが作るキャッシュ・パスワードの入った設定など、記録しないファイルは .gitignore に書いて無視させます。一覧のファイルを右クリックすると、次のメニューが出ます（logs/debug.log を右クリックしたときの例）。

項目.gitignore に書き足す行無視されるもの
このファイルを無視する/logs/debug.logそのファイルだけ
拡張子 .log のファイルをすべて無視する*.logどのフォルダの .log も
フォルダ logs/ を無視する/logs/そのフォルダの中すべて（すぐ上のフォルダと、いちばん上のフォルダを選べます）
.gitignore を編集….gitignore を直接書き換える（下の説明）

頭の / は「リポジトリのいちばん上から数えた場所」という意味で、その場所だけに当てはまります。書き足したあとは .gitignore 自身が変更として出るので、ほかの変更と一緒にコミットします。

すでに git で管理しているファイル（一度コミットしたファイル）は、.gitignore に書くだけでは無視されません。そのときは確認の画面が出て、管理から外して無視できます（git rm --cached -- ファイル、フォルダなら git rm -r --cached -- フォルダ/）。ファイルは PC に残り、次のコミットで記録から外れます。GitHub からも消えるので、ほかの人がプルすると、その人の手元からも消えます。

.gitignore を編集…（右クリック、または その他 ▾）では、.gitignore を直接書き換えられます。書きまちがえた行を消すときなどに使います。Ctrl＋S で保存します。まだ .gitignore がなければ、保存したときにリポジトリのいちばん上に作ります。

コミットする

下のコミット欄で、変更に説明を付けて記録します。

項目説明
変更の要約（必須）何をしたかを短く書きます（例: 「ログイン画面のボタンの色を直す」）。
説明（任意）くわしい説明。
要約の末尾に Issue 番号を付ける要約の最後に (#12) のように付けます。GitHub で Issue とコミットがつながります。
マージされたら #番号 を閉じる説明に Closes #12 を付けます。既定のブランチに取り込まれると、Issue が自動で閉じます。
直前のコミットを修正する（amend）直前のコミットに、今の変更と要約を入れ直します。まだ GitHub に送っていないコミットだけ直せます。
変更なしでコミットする（空コミット）ファイルを変えずにコミットします。区切りを付けたいときや、GitHub の Actions を動かしたいときに使います。

欄の下に、実行するコマンドが表示されます。コミット（Ctrl＋Enter）でコミットし、コミットしてプッシュ で、そのまま GitHub にも送ります。

git commit -m "ログイン画面のボタンの色を直す (#12)" -m "Closes #12"

変更を持って切り替える変更をそのまま持っていきます。同じファイルがぶつかると切り替えられません。

GitHub に送ったコミットの書き換えに注意

リセットやリベース、amend は、コミットを作り直したり、ブランチから外したりします。すでに GitHub に送ったコミットを書き換えると、GitHub の履歴と食い違い、送り直すのに強制プッシュが必要になります。Life Manager では、送り済みのコミットの amend はできないようにしています。

競合（コンフリクト）したとき

プル・マージ・チェリーピック・退避した変更を戻す などで、同じファイルの同じところが両方で変わっていると、git は自動でまとめられずに止まります。これが競合です。作業タブの上に「〇〇の途中です」と表示され、競合したファイルが「競合」の欄に出ます。

  1. 競合したファイルをエディタで開きます。次のような印が入っています。
    <<<<<<< HEAD 今のブランチの内容 ======= 取り込もうとした内容 >>>>>>> feature
  2. どちらを残すか（または両方をまとめるか）を決めて書き直し、印の行をすべて消して保存します。
  3. 作業タブで、そのファイルにチェックを入れます（git add。「直した」という合図です）。
  4. すべて直したら、次へ進みます。
    • マージの途中なら: コミットすると、マージが完了します。
    • リベース・チェリーピック・リバートの途中なら: 続ける を押します（git rebase --continue など）。

やめたいときは 〇〇を中止… を押すと、始める前の状態に戻ります（git merge --abort など）。

リポジトリ repository

クローン git clone
GitHub のリポジトリを、履歴ごと PC にコピーすること。
コミット git commit
変更を、要約を付けて履歴に記録すること。記録した 1 つ 1 つもコミットと呼びます。
ハッシュ

ステージ git add
次のコミットに入れる変更を選ぶこと。選んだ変更の置き場所もステージ（インデックス）と呼びます。

git で記録しない（無視する）ファイルを、1 行に 1 つ書いておくファイル。すでに記録しているファイルには効かないので、git rm --cached で管理から外します。

変更の中身。追加した行と削除した行で表します。

作業を分けて進めるための流れ。ブランチは、その流れの先頭のコミットを指す「しおり」のようなものです。

GitHub で最初に表示されるブランチ（多くは main）。完成したものをまとめる場所として使います。

今作業しているブランチ（コミット）が HEAD です。ブランチを切り替えることをチェックアウトと呼びます。

ブランチではなく、コミットそのものを取り出している状態。ここでコミットしても、どのブランチにも属しません。続けて作業するなら、ブランチを作ります。
マージ git merge
別のブランチの変更を、今のブランチに合流させること。
リベース git rebase
今のブランチのコミットを、別のブランチの先に作り直すこと。履歴が一直線になりますが、コミットは作り直されます。
チェリーピック git cherry-pick
ほかのブランチの特定のコミットだけを、今のブランチに取り込むこと。
リバート git revert
あるコミットの変更を打ち消す、新しいコミットを作ること。履歴は消しません。
リセット git reset
ブランチを前のコミットまで戻すこと。後のコミットはブランチから外れます。
競合（コンフリクト）
同じところが両方で変わっていて、git が自動でまとめられない状態。
退避（スタッシュ） git stash
コミットせずに、変更を一時的にしまっておくこと。
タグ git tag
コミットに付ける名前。リリースの区切り（v1.0.0 など）に使います。
リモート・origin
GitHub など、PC の外にあるリポジトリ。クローン元には origin という名前が付きます。origin/main は「GitHub にある main の位置（最後にフェッチしたとき）」です。
上流ブランチ
プッシュ・プルの相手になる、GitHub のブランチ。
フェッチ・プル・プッシュ
フェッチは GitHub の最新の状態を取ってくるだけ、プルは取ってきて今のブランチに取り込む、プッシュは自分のコミットを GitHub に送ることです。
amend
直前のコミットを作り直して、変更や要約を直すこと。
空コミット
ファイルの変更を含まないコミット（git commit --allow-empty）。

マイルストーン

期限つきの目標を管理します。Issue をマイルストーンに結びつけると、目標に対する進み具合が見えます。

  1. ＋ マイルストーン を押します。
  2. 名前（必須）・説明・期日を入れて、作成 を押します。

カードには、完了した Issue の割合（進捗バー）、完了数 / 全体の数、期日が出ます。見積もりの付いた Issue があれば、見積 5/13pt（閉じた Issue の見積もりの合計／全部の合計）も出ます。

ガントチャート

ルーチン

毎日・毎週・毎月、決まった時刻に Issue を自動で作る機能です。日報や定期的な確認に使えます。

  1. ＋ ルーチン追加 を押します。
  2. 名前・頻度（毎日／毎週／毎月）・曜日・時刻・Issue のタイトル・ラベル・本文・自動で閉じる時刻（任意）を決めます。
  3. 保存 を押します。

{{week}}2026年第11週

サブイシュー（親子）

詳細の 🧩 サブイシュー の欄に、子の Issue の一覧と、いくつ終わったか（2 / 5 完了 とバー）が出ます。GitHub の画面でも同じ親子で見えます。

  • 子を作る: タイトルを入れて Enter。ラベルは「種別:イシュー」「状態:未整理」と親の「分野」、マイルストーンは親と同じになります。
  • 今ある Issue を子にする: 既存の Issue をつなぐ… を押し、番号かタイトルで探して選びます。ほかの親の子なら、付け替えます。
  • 子から外す: 行の ×。親子のつながりを外すだけで、Issue は消えません。
  • 子の ○ を押すとクローズ、題名を押すとその子の詳細が開きます。子の詳細のいちばん上の ↑ 親：#45 … で親に戻れます。

タスク・ボード・マイルストーンのカードには、子のある Issue に 🧩 2/5（子 5 件のうち 2 件が完了）、子の Issue に ↑ #45 親の題名 が出ます。子を全部クローズしても、親は自動では閉じません。サブイシューは、GitHub につながっているときだけ使えます。

クローズ ▾ から、GitHub と同じ 3 つの閉じ方を選べます。閉じた Issue の上には「Closed（完了）」のように、閉じ方が出ます。

閉じ方使うとき

⊘ 予定なしとして閉じるやらないことにした

🔗 関連

意味の近い Issue を結びます（ガントの「先行」とは別で、日程には関係しません）。＋ 関連を足す で、番号かタイトルで探して選びます。結んだ相手の Issue の詳細にも出ます（「#6 の側で結んだ」のように、どちらで結んだかも出ます）。× で外しても、Issue は消えません。関連は、本文の見えない印（<!-- related:#12 -->）に残します。

コメントと変更の履歴

  • 作った・ラベルを付けた／外した・担当・マイルストーン・題名の変更・閉じた（閉じ方）・開き直した・子を足した など

チームで使う（管理者向け）

リーダーが、メンバーのトークンを作って配らないでください

トークンは、作った人の「合鍵」です。人のトークンを使うと、だれが操作したかが分からなくなり、その人のほかのリポジトリまで触れてしまいます。メンバーはそれぞれ、自分の GitHub アカウントで GitHub でログイン します。リーダーがすることは、リポジトリ（または組織）に招待することだけです。

メンバーとして参加する

  1. GitHub のアカウントを作ります（まだないとき）。
  2. リポジトリへの招待を受けます。メールの「View invitation」→「Accept invitation」、または教えてもらった招待の URL を開いて「Accept invitation」を押します。
    リポジトリのページ（https://github.com/オーナー名/リポジトリ名）が見られれば参加できています。
  3. Life Manager で GitHub でログイン し、使うリポジトリを一覧から選びます（「初期セットアップ」）。
  4. 組織のリポジトリで「組織の許可がまだです」と出たら、組織に許可をお願いする を押し、管理者に許可してもらいます（最初の一度だけ）。

Organization を使う（おすすめ）

2 人以上で続けて使うときは、GitHub の Organization（無料）がおすすめです。人ではなく Organization がリポジトリを持つので、人が抜けても残り、権限をチーム単位で管理できます。

  1. Organization を作ります（Settings → Organizations → New organization、Free プランで可）。
  2. Organization の中にリポジトリを作ります（Private がおすすめ）。
  3. メンバーを招待し（Organization Settings → Members → Invite member）、Write 以上の役割を付けます。
  4. Life Manager を許可します（一度だけ）。新しい Organization は、外部のアプリが非公開のリポジトリを使うのに、管理者の許可がいる設定になっています。メンバーから届いたお願い（メール）から許可するか、Organization の Settings → Third-party Access → OAuth app policy で Life Manager を許可します。

個人のリポジトリで使うときは、Settings → Collaborators → Add people でメンバーを招待し、Write 以上の役割を付けます（組織の許可はいりません）。

トークンで使うときの注意

Fine-grained token でリポジトリを選ぶとき、出てくるのは「自分が持ち主のリポジトリ」と「入っている Organization のリポジトリ」だけです。ほかの人の個人リポジトリに招待された場合は出てきません。そのときは GitHub でログイン を使うか、Organization に移します。トークンは、プロジェクト専用のトークン → いつものトークン の順に使われます。

git の作業をチームで行うときの流れ（例）

  1. Issue を作り、担当を決める。
  2. 作業タブで Issue を選び、Issue 用のブランチ（issue-12 など）を作る。
  3. 変更をコミットして、プッシュする。
  4. GitHub でプルリクエストを作り、レビューしてから既定のブランチにマージする（要約に Closes #12 があれば、Issue が自動で閉じる）。

よくある質問・困ったとき

上の「未送信」がなかなか消えません
まだ GitHub につながっていないか、トークンが無効になっているかもしれません。未送信 を押すと、送れなかった理由が出ます。トークンが無効のときは、設定 → 接続 の「GitHub トークン」で、ログインし直すかトークンを入れ直してください（「つながらないとき」）。
「git が見つかりません」と出ます
Git が入っていません。設定 → 接続 → 作業フォルダ の Git をインストールする… から入れてください。入れたあとも見つからないときは、アプリを開き直してください。
プッシュやプルで「GitHub へのログインが必要です」と出ます
この PC の git が、まだ GitHub にログインしていません。Windows では、はじめてのプッシュのときにログインの画面（ブラウザ）が出ることがあります。出ないときは、その他 ▾ → このフォルダでターミナルを開く で、同じ操作（git push など）を一度打ってログインしてください。
プッシュが「拒否された（rejected）」と出ます
GitHub の方に、まだ取り込んでいないコミットがあります。先に ⬇ プル で取り込んでから、もう一度プッシュしてください。
コミットできません
コミットするファイルにチェック（ステージ）が入っているかを確かめてください。「名前とメールアドレスが決まっていません」と出るときは、設定 → 接続 → 作業フォルダ の 使う準備を確かめる から決めてください。
作業フォルダに選べません
選べるのは、設定しているリポジトリをクローンしたフォルダだけです。まだ PC にない場合は GitHub からクローン… を使ってください。
学校の PC で Git がインストールできません
インストールには PC の管理者の確認が必要です。PC の管理者に Git のインストールを頼んでください（https://git-scm.com/downloads）。
データはどこに保存されますか？
すべて GitHub のリポジトリ（Issue・マイルストーン・ラベル）に保存されます。ルーチンや通知の設定は、リポジトリの config/ フォルダに保存されます。アプリを消しても、データは GitHub に残ります。作業フォルダの場所や表示の設定は、この PC だけに保存されます。
画面の上に「トークンの期限が…」「トークンが使えません」と出ます
設定 → 接続 の「GitHub トークン」で、GitHub でログインし直す（トークンで使っているときは トークンを入れる…）を押してください。プロジェクト専用のトークンなら、その行の 入れ替える… から入れ直します。GitHub でログインした場合は、期限はありません。
学校の PC で使い終わったら？
設定 → 接続 の ログアウト を押してください。この PC から、あなたのトークンがすべて消えます。GitHub 側でもやめたいときは、GitHub の Settings → Applications から Life Manager を取り消します。
チームのリポジトリが一覧に出てきません
招待を受けているか（メールの「Accept invitation」）、組織が Life Manager を許可しているかを確かめてください（「チームで使う」）。URL を貼って選ぶと、何が足りないかが出ます。
複数のリポジトリを使えますか？
使えます。設定 → 接続 の プロジェクト管理 で登録し、サイドバーのプルダウンで切り替えます。作業フォルダも、リポジトリごとに決められます。
ガントチャートに帯が出ません
Issue の詳細の「ガントチャート」の欄で、開始日と終了日を決めてください。
オフラインで使えますか？
タスク管理は GitHub に接続するため、オフラインでは使えません。git の作業（ステージ・コミットなど）は PC の中で行えますが、プッシュ・プル・フェッチには接続が必要です。
